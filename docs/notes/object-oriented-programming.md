## 导语

面向对象编程（OOP）是一种基于对象的编程范式——对象是封装数据与函数的软件实体。

一个 OOP 计算机程序由彼此交互的对象组成。OOP 语言是提供面向对象编程特性的语言，但由于构成 OOP 的特性集合存在争议，将一种语言归类为 OOP——以及它在何种程度上支持 OOP——是可争论的。由于范式并非互斥，一种语言可以是多范式的（即被归类为不止 OOP）。

## 历史

“对象”这一想法在编程中始于 1950 年代末与 1960 年代初麻省理工学院（MIT）的人工智能小组。在那里，“对象”指的是带有已识别属性（attributes）的 LISP 原子。另一个早期例子是 Ivan Sutherland 于 1960–1961 年在 MIT 创建的 Sketchpad。在其技术报告的术语表中，Sutherland 定义了诸如“对象”与“实例”等术语（类的概念则由“master”或“definition”涵盖），尽管这些术语专门针对图形交互。后来，在 1968 年，AED-0——MIT 版本的 ALGOL 编程语言——将数据结构（“plexes”）与过程连接起来，预示了后来被称为“消息”、“方法”与“成员函数”的概念。数据抽象与模块化编程等主题在当时是常见讨论点。

与此同时，在挪威，Simula 于 1961–1967 年间被开发。Simula 引入了基本的面向对象思想，例如类、继承与动态绑定。Simula 主要由从事物理建模的研究者使用，例如船舶及其货物在货运港口中的移动。Simula 通常被公认为是第一种具备面向对象语言主要特性与框架的语言。

我把对象想成类似生物细胞，和/或网络上的独立计算机，只能通过消息通信（因此消息传递从一开始就存在——要弄清如何在编程语言中足够高效地做消息传递以便有用，花了一些时间）。

—— Alan Kay

受 MIT 与 Simula 两者影响，Alan Kay 于 1966 年 11 月开始发展他自己的想法。他后来会创建出 Smalltalk——一种有影响力的 OOP 语言。到 1967 年，Kay 已在对话中使用“面向对象编程”这一术语。尽管有时被称为 OOP 的“之父”，Kay 说过他的想法与 OOP 通常被理解的方式不同，并暗示计算机科学建制并未采纳他的观念。一份由 Barbara Liskov 合著的 1976 年 MIT 备忘录列出 Simula 67、CLU 与 Alphard 作为面向对象语言，但并未提及 Smalltalk。

在 1970 年代，Smalltalk 编程语言的第一个版本由 Alan Kay、Dan Ingalls 与 Adele Goldberg 在 Xerox PARC 开发。Smalltalk-72 以在语言层面使用对象及其图形开发环境而著称。Smalltalk 是一个完全动态的系统，允许用户在工作过程中创建与修改类。OOP 理论的许多内容是在 Smalltalk 的语境中发展出来的，例如多重继承。

在 1970 年代末与 1980 年代，OOP 崛起并获得显著地位。面向对象 Lisp 的 Flavors 自 1979 年起被开发，引入了多重继承与 mixins。1981 年 8 月，《Byte》杂志突出介绍了 Smalltalk 与 OOP，将这些思想介绍给广泛受众。LOOPS——Interlisp-D 的对象系统——受到 Smalltalk 与 Flavors 的影响，一篇关于它的论文于 1982 年发表。1986 年，第一届面向对象编程、系统、语言与应用会议（OOPSLA）有 1,000 人参加。这次会议标志着整合 Lisp 对象系统的努力开始，最终导致了 Common Lisp Object System。在 1980 年代，有少数尝试设计在内存中包含对象硬件支持的处理器架构，但这些并不成功。例子包括 Intel iAPX 432 与 Linn Smart Rekursiv。

在 1980 年代中期，出现了诸如 Objective-C、C++与 Eiffel 语言等新的面向对象语言。Objective-C 由 Brad Cox 开发，他曾在 ITT Inc. 使用过 Smalltalk。Bjarne Stroustrup 基于他在博士论文中使用 Simula 的经验创建了 C++。Bertrand Meyer 于 1985 年完成了 Eiffel 语言的第一个设计，其焦点是使用契约式设计方法提升软件质量。

在 1990 年代，OOP 成为主要的编程方式，尤其是随着更多语言支持它。这些包括 Visual FoxPro 3.0、C++ 与 Delphi。随着图形用户界面的兴起——界面用对象表示按钮、菜单及其他元素——OOP 变得更加流行。一个著名例子是 Apple 的 Cocoa 框架，用于 macOS，并以 Objective-C 编写。OOP 工具包也增强了事件驱动程序设计的流行度。

在苏黎世联邦理工学院（ETH Zürich），Niklaus Wirth 及其同事创造了 OOP 的新路径。Modula-2（1978）与 Oberon（1987）包含了一种对对象定向、类以及跨模块边界类型检查的独特方法。继承在 Wirth 的设计中并不显眼，因为他的术语体系朝相反方向看：它被称为类型扩展（type extension），视点是从父级向下到继承者。

许多最初在 OOP 流行之前开发的编程语言后来被增强了面向对象特性，包括 Ada、BASIC、Fortran、Pascal 与 COBOL。

## 特性

语言所提供的 OOP 特性各不相同。以下是 OOP 语言的一些常见特性。将 OOP 与其他风格（例如关系式编程）进行比较是困难的，因为并不存在一个清晰、约定俗成的 OOP 定义。

### 封装与信息隐藏

信息隐藏与封装可以指若干相关概念：

- 内聚（Cohesion），将相关字段与方法保持在一起。字段（亦称属性或性质）以变量形式包含信息（亦称状态）。方法（亦称函数或动作）通过逻辑代码定义行为。
- 解耦（Decoupling），组织代码使得只有数据的某些部分被相关函数使用。解耦使在不改变代码库其他部分的情况下改变对象内部工作方式变得更容易，例如在代码重构中。对象充当其内部运作与外部消费代码之间的边界。
- 数据隐藏（Data hiding），将对象的内部细节对外部代码隐藏。消费代码只能通过其公共成员与对象交互，因为语言提供了控制可见性的访问修饰符。

一些编程语言，例如 Java，通过可见性关键字（`private` 与 `public`）提供信息隐藏。一些语言例如 Python 不提供可见性特性，但开发者可能遵循诸如以 underscore 开头命名私有成员的约定。也存在中间级别的访问，例如 Java 的 `protected` 关键字（允许来自同一类及其子类的访问，但不允许不同类的对象访问），以及 C#、Swift 与 Kotlin 中的 `internal` 关键字，它将访问限制在同一模块内的文件。

信息隐藏与数据抽象的支持者说，它使代码更易于复用，并直观地表示现实世界情境。然而，另一些人主张 OOP 并不增强可读性或模块性。Eric S. Raymond 写过，OOP 语言倾向于鼓励厚重分层的程序，从而破坏透明性。Raymond 将此与 Unix 与 C 语言所采取的方法作不利比较。

SOLID 包括开闭原则，它说类与函数应当“对扩展开放，对修改关闭”。Luca Cardelli 曾表示，OOP 语言“在类扩展与修改方面具有极其糟糕的模块性属性”，并且往往极其复杂。后一点由 Erlang 的主要发明者 Joe Armstrong 重申，他被引述说：

面向对象语言的问题在于它们随身携带了所有这些隐式环境。你想要一根香蕉，但你得到的是一只拿着香蕉的猩猩以及整片丛林。

Leo Brodie 说，信息隐藏可能导致重复代码，这违背软件开发中的不要重复自己（don't repeat yourself）规则。

### 继承

继承可以通过类或原型得到支持，二者存在差异，但使用诸如对象与实例等相似术语。

### 基于类

在基于类的编程中——最常见的 OOP 类型——对象是类的一个实例。类定义数据（变量）与方法（逻辑）。对象通过构造函数创建。该类的每个实例都具有同一组变量与方法。元素可以包括：

- 类变量——属于类本身；该类的所有对象共享一份拷贝
- 实例变量——属于一个对象；每个对象都有这些变量自己的版本
- 成员变量——指一个类的类变量与实例变量两者
- 类方法——只能使用类变量
- 实例方法——属于一个对象；可以使用实例变量与类变量两者

类可以从其他类继承，从而创建类的层次结构：子类从超类继承的情况。例如，一个 `Employee` 类可能从 `Person` 类继承，这使 Employee 对象具有来自 `Person` 的变量。子类可以添加不影响超类的变量与方法。大多数语言也允许子类覆盖超类方法。一些语言支持多重继承，其中一个类可以从多于一个类继承，其他语言则以类似方式支持 mixins 或 traits。例如，一个名为 UnicodeConversionMixin 的 mixin 可能向 FileReader 与 WebPageScraper 类两者添加方法 unicode_to_ascii()。

抽象类不能被直接实例化为对象。它只被用作超类。

其他类是工具类，它们只包含类变量与方法，且不打算被实例化或子类化。

### 基于原型

在基于原型的编程中，并不提供类概念，而是把一个对象链接到另一个对象，称为其原型或父级。在 Self 中，一个对象可以有多个或没有父级，但在最流行的基于原型语言 JavaScript 中，一个对象恰好有一条原型链接，直到其原型为 null 的基对象。

原型充当新对象的模型。例如，如果你有一个对象 `fruit`，你可以制作两个对象 `apple` 与 `orange`，它们共享 `fruit` 原型的特征。基于原型的语言也允许对象拥有它们自己的独特属性，因此 `apple` 对象可能有一个属性 `sugar_content`，而 `orange` 或 `fruit` 对象则没有。

### 无继承

在所有 OOP 语言中，通过对象组合，一个对象可以包含其他对象。例如，一个 `Employee` 对象可能包含一个 `Address` 对象，连同诸如 `name` 与 `position` 等其他信息。组合是一种“has-a”关系，例如“一个雇员有一个地址”。一些语言，例如 Go，不支持继承。相反，它们鼓励“组合优于继承”，对象用更小的部分构建，而不是父子关系。例如，Employee 类可以不从 Person 类继承，而只是包含一个 Person 对象。这让 Employee 类控制它向程序其他部分暴露多少 Person。委托是另一种可用作继承替代的语言特性。

程序员对继承有不同意见。C++ 的作者 Bjarne Stroustrup 曾表示，可以在没有继承的情况下做 OOP。Rob Pike 批评继承会创建复杂层次结构，而不是更简单的解决方案。

### 继承与行为子类型

人们常常认为，如果一个类从另一个类继承，就意味着子类“是”原类的一个更具体版本。这假定程序语义是：来自子类的对象总是可以无问题地替换来自原类的对象。这一概念被称为行为子类型，更具体地说是里氏替换原则。

然而，这常常并不成立，尤其是在允许可变对象——创建后会改变的对象——的编程语言中。事实上，OOP 语言中由类型检查器强制的子类型多态，在大多数——即便不是全部——语境中都不能保证行为子类型。例如，圆–椭圆问题以 OOP 的继承概念处理时出了名地困难。行为子类型一般是不可判定的，因此无法由编译器轻易实现。正因为如此，程序员必须仔细设计类层次结构，以避免编程语言本身无法捕捉的错误。

### 动态分派

方法可以通过动态分派被调用，使得方法在运行时而非编译时被选择。如果方法选择依赖于多于一种对象类型（例如作为参数传入的其他对象），它被称为多重分派。在此语境中，方法调用也被称为消息传递，意思是方法名及其输入像发送给对象以使其行动的消息。

动态分派与继承协同工作：如果一个对象没有被请求的方法，它向上查找其父类（委托），并沿链继续查找匹配的方法。

### 多态

OOP 中的多态指子类型化或子类型多态，其中一个函数可以与特定接口一起工作，从而以统一方式操纵不同类的实体。

例如，想象一个程序有两种形状：一个圆与一个正方形。两者都来自一个名为“Shape”的共同类。每种形状都有自己的绘制方式。借助子类型多态，程序不需要知道每种形状的类型，而可以简单地为每种形状调用“Draw”方法。编程语言运行时将确保为每种形状运行正确版本的“Draw”方法。因为每种形状的细节在它们自己的类内部处理，这使代码更简单、更有组织，并实现了强关注点分离。

### 开放递归

一个对象的方法可以访问该对象的数据。许多编程语言使用一个特殊词，例如 this 或 `self`，来指代当前对象。在支持开放递归的语言中，一个对象中的方法可以使用这个特殊词调用同一对象中的其他方法，包括它自己。这允许一个类中的方法调用后来在子类中定义的另一个方法，这一特性被称为迟绑定。

## 设计模式

设计模式是软件设计中问题的常见解决方案。一些设计模式对 OOP 特别有用，并且设计模式通常在 OOP 语境中被引入。

### 现实世界建模与关系

有时，对象以数字形式表示现实世界的事物与过程。例如，一个图形程序可能有诸如 `circle`、`square` 与 `menu` 等对象。一个在线购物系统可能有诸如 `shopping cart`、`customer` 与 `product` 等对象。Niklaus Wirth 说：“这一范式［OOP］紧密反映现实世界中系统的结构，因此非常适合为具有复杂行为的复杂系统建模。”

然而，更常见的是，对象表示抽象实体，例如一个打开的文件或一个单位转换器。并非所有人都同意 OOP 使精确复制现实世界变得容易，或者这样做甚至是必要的。Bob Martin 认为，因为类是软件，它们的关系并不匹配它们所表示的现实世界关系。Bertrand Meyer 主张，程序不是世界的模型，而是世界某一部分的模型；“现实是隔了两代的表亲”。Steve Yegge 指出，自然语言缺乏 OOP 那种在动作（方法）之前先命名事物（对象）的方式，而函数式编程则相反。这可能使 OOP 解决方案比用过程式编程写出的方案更复杂。

### 对象模式

以下是 OOP 对象的显著软件设计模式。

- 函数对象：具有一个主要方法、行为像匿名函数的类（在 C++ 中为函数运算符 `operator()`）
- 不可变对象：创建后不改变状态
- 一等对象：可以不受限制地使用
- 容器对象：包含其他对象
- 工厂对象：创建其他对象
- 元对象：用于创建其他对象（类似于类，但是一个对象）
- 原型对象：一种通过复制自身创建新对象的特化元对象
- 单例对象：在程序生命周期内是其类的唯一实例
- 过滤器对象：接收数据流作为输入，并将其变换为该对象的输出

一个常见的反模式是上帝对象，一个知道或做了太多事情的对象。

### 四人帮设计模式

《设计模式：可复用面向对象软件的要素》是一本著名的书，于 1994 年由四位作者出版：Erich Gamma、Richard Helm、Ralph Johnson 与 John Vlissides。人们常称他们为“四人帮”。该书讨论 OOP 的优点与弱点，并解释 23 种解决编程问题的常见方式。

这些解决方案，称为“设计模式”，被分为三种类型：

### 面向对象与数据库

OOP 与关系数据库管理系统（RDBMS）在当今软件中都被广泛使用。然而，关系数据库并不直接存储对象，这在一起使用它们时造成挑战。这一问题被称为对象–关系阻抗不匹配。

为解决这一问题，开发者使用不同方法，但没有一种是完美的。最常见的解决方案之一是对象–关系映射（ORM），它帮助将面向对象程序连接到关系数据库。ORM 工具的例子包括 Visual FoxPro、Java Data Objects，以及 Ruby on Rails ActiveRecord。

一些被称为对象数据库的数据库被设计为与 OOP 一起工作。然而，它们并未像关系数据库那样流行或成功。

Date 与 Darwen 提出了一个理论基础，把 OOP 作为一种可定制类型系统来支持 RDBMS，但它禁止对象包含指向其他对象的指针。

### 责任驱动设计 vs. 数据驱动设计

在责任驱动设计中，类围绕它们需要做什么以及它们以契约形式共享的信息来构建。这与数据驱动设计不同，在数据驱动设计中，类基于它们需要存储的数据来构建。据责任驱动设计的提出者 Wirfs-Brock 与 Wilkerson 所说，责任驱动设计是更好的方法。

### SOLID 与 GRASP 指南

SOLID 是由 Michael Feathers 创建的一套五条设计良好软件的规则：

- 单一职责原则：一个类应当只有一个改变的理由。
- 开闭原则：软件实体应当对扩展开放，对修改关闭。
- 里氏替换原则：使用指向或引用基类的指针或引用的函数，必须能够在不知情的情况下使用派生类的对象。
- 接口隔离原则：客户端不应当被强迫依赖它们不使用的接口。
- 依赖倒置原则：依赖抽象，而非具体。

GRASP（一般责任分配软件模式）是由 Craig Larman 创建的另一套软件设计规则，帮助开发者把责任分配给程序的不同部分：

- 创建者原则：允许类创建它们紧密使用的对象。
- 信息专家原则：把任务分配给拥有所需信息的类。
- 低耦合原则：减少类依赖以提升灵活性与可维护性。
- 高内聚原则：设计具有单一、聚焦职责的类。
- 控制器原则：把系统操作分配给管理流程与交互的独立类。
- 多态：允许不同类通过共同接口被使用，促进灵活性与复用。
- 纯虚构原则：创建辅助类以改善设计、提升内聚并降低耦合。
