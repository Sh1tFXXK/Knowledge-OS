## 〇、结论

**判定：C —— 当前挂载本身就是错误模型**（并含 **B** 的宿主成分）。

## 二、A / B / C 逐条驳立

### A. 「MySQL 领域下的真实语义节点」—— 部分成立，但不足以支撑「给名字」

**成立的**：池侧确实承载真实 MySQL 领域知识（`kind=concept`），内容来自原节点 #112 的拆分。

**不成立的**：
1. **它们不是本体维度，是「工具网格」**。a-split 规格里它们被放进 `layout: 'grid'` 的 `mysql_service_tools_grid`，定位是**宿主的维度展示项**（`tools[i]` 直接作为 `atoms.nodeId`）。「工具/入口/管理面」是**目录性质**的东西，不构成一个本体分支。
2. **语义位已被占据**。见 §1.5：`备份/恢复` 已有 9,758 字的规范子树；`集群管理工具` 与同层 0 字的 `Cluster` 同义；`备份恢复工具` 与同层 `MySQL 备份`(107字)/`MySQL 恢复`(84字) 重叠。
3. **零结构依赖**。3 条出边均为 0 —— 树里没有任何东西需要它们存在。

### B. 「projection/reference 节点，应另走结构治理」—— 不成立为**主**判定

这 3 条**自身不是** projection 节点（它们是 `asplit_*`）。成立的是它们的**宿主**属于那一类。

**且「以 `projection:` 开头」绝不能作为定罪依据** —— 见 §三 判据审计，这是本批最大的一处**误报陷阱**。

### C. 「当前挂载本身就是错误模型」—— ✅ 成立（主判定）

成立的三个支点：
1. **宿主是空壳 + 导入命名空间 id**：自身 0 字、`kind`/`role` 未定义、treeId 属 `projection:` 族。
2. **同层是未整合的合并区**：4 种 id 规范 / 10 个子 / 4 个 0 字占位 / 同层语义重复。
3. **挂载是刻意写入的临时宿主**：源码显示 `hostTree` 显式等于该 projection id，原节点正文被停在宿主 tab 里 —— 这是一次 a-split 的**中转停靠**，不是一次经过裁决的归位。

## 四、为什么**绝不能**给它们造 `tree_mysql_*` 名字

两条硬理由，均与「名字好不好听」无关：

1. **会把一个观测/导入层产物永久钉进祖先链。**
   这 3 条的父是 `projection:…`。一旦给它们语义 id，该投影 id 就从一个**临时宿主**变成了**永久语义祖先** —— 此后所有基于「祖先链语义化程度」的判据（含 T3 自己的 `semanticAncestorGap`）都会把它当作既成事实。这直接违反 §3.1（挂载位置不是身份证据）与 ADR-0002。

2. **会与既有规范体系形成永久重复。**
   本库 `tree_mysql_instance_*` 已有 **53 条**，且 `恢复系统` 子树（9,758 字 / 37 节点）已把「MySQL 备份/恢复」这个语义位完整占住，其中还包括一条 `MySQL 备份 / backup`（350 字）。再造 `tree_mysql_tool_backup` 之类的名字，等于在同一个语义位上盖第二栋楼。

> 这正是用户坚持的那条纪律：**「不应该强行给它们造一个 `tree_mysql_*` 名字」**。

## 五、推荐处置与可行性技术前提

### 5.1 推荐：**卸树留池**（option D）

**做法**：把 3 条从树卸下（`unloadTreeEntry`），**保留池实体与 `belongs-to` 边**。

**为什么可行 —— 已实证**：
- **它们本来就是维度原子**：a-split 规格里 `tools[0..2]` 直接就是 `dims.atoms[].nodeId`（§1.4）。
- **维度原子走池查表、零树依赖**：
  `src/core/sections/GridSection.tsx:19` → `const node = nodePool[atom.nodeId];`
  `src/core/sections/ChainSection.tsx:19` → `const node = nodePool[atom.nodeId];`
  渲染所需字段全部来自池：`node.label` → 标题 · `atom.desc ?? node.card.tabs[0]?.content` → 描述 · `node.role` → 角标。
- ⇒ **卸树后，宿主「服务层」的「服务层工具」网格仍会完整显示这 3 个原子。**

**收益**：
- `BLOCK 3 → 0`，**全程不需要任何命名决策**；
- 不产生 `pod` 期投影 id 被固化的后果；
- T3 前置范围 **133 → 130**（3 条退出树，其 asplit treeId 随之消失，无需再为其定名）。

**必须一并声明的代价（不掩盖）**：
- 树中「服务层」这一层变得更空（若不顺带清理，宿主的 10 个子仍是 4 种规范 + 4 个空壳）；
- 3 条在**树导航**里不再出现，只在宿主的维度网格里出现 —— 这是**有意的语义降级**（从「本体节点」降为「展示原子」），符合「工具/入口不是本体维度」的判断。

### 5.2 备选一：**重新归位**（需要更大批次，**不建议现在做**）

若要保留它们在树中，**前提是先治理容器脊梁**：`服务层`（projection 空壳）→ `结构`/`MySQL Server`（colon 族）→ `MySQL`（段位 `_s15_`）→ `数据库产品`（chapter）→ `数据库`（demo）。这是**容器层命名治理**，范围与根因都不同于 T3 的「原子项命名」。**在脊梁未治理前归位，只是把问题往下挪一层。**

### 5.3 备选二：**并入既有体系**（仅适用于「集群管理工具」）

`集群管理工具`（71 字）与同层 `Cluster`（**0 字**）构成真重复对，可考虑保留有内容者、清掉空壳。但该动作**仍需先决定容器**，且「备份恢复工具」并不能并入（「工具」与「备份类型」是不同 kind）。⇒ 不建议作为本批的通用处置。

### 5.4 与 T3 读数的关系

| 处置 | T3 前置范围 | 读数 |
|---|---|---|
| 卸树留池（推荐） | **130** | `HIGH 92 / MEDIUM 38 / BLOCK 0` |
