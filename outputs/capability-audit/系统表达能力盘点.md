## 1. 例子：MySQL 锁机制（`demo_lock`）

### 1.1 想表达的知识

问题库里挂着 `q_lock_1`「MySQL 有哪些锁类型？」，答案是一段 4 分类清单（来自《深入浅出 MySQL》）。对应到节点上，就是这个节点的一个维度、5 个 section：

| 想表达 | 存成什么 | section |
|---|---|---|
| 按锁粒度 | grid，3 个原子 | `lock_grain_grid` |
| 按存储引擎 | grid，4 个原子 | `lock_engine_grid` |
| 按操作类型 | grid，2 个原子 | `lock_type_grid` |
| 按锁策略 | grid，2 个原子 | `lock_strategy_grid` |
| 粒度 × 开销/死锁/并发 的对比 | **matrix**，3 个原子各带 4 个 attrs | `lock_grain_matrix` |

维度本身有名字和提示语：

```
id: lock_composition   name: 多维分类   color: #E58522
hint: 同一批锁原子，按粒度/引擎/操作/策略四套规矩分别投影；
      粒度对比矩阵归属本节点结论区，子节点引用并高亮自己。
```

**这句话是理解整个表达体系的关键**：dimension 是"一套规矩"（一个视角），section 是这套规矩下的一个个子结构，`atoms` 只放引用（`{nodeId, attrs?, desc?}`），原子本体在节点池里。

### 1.3 一处真实的重叠（不是我设计的，是跑出来的）

`demo_lock` 的 dimension 没有声明 `scope`，于是走默认值（`OrthogonalMatrixView.tsx:108-115`）：`{id:'default_parts', name:'分类矩阵', target:'parts'}`。

`target !== 'object'` 时走 `BandScopeView`，行的分类来源有两条路（`:243-246`）：

1. 有 `dimension.groups` → 用语义组；
2. 没有 → **退回用 section 标题当分类**。

这个例子里 `groups: []`，所以走第 2 条。此时列的顺序是 `buildOrderedAtoms` 定的（`:121-140`：只取每个维度的 primarySection，去重，首次出现优先）→ 列 = `[表级锁, 行锁, 页面锁]`；于是：

- `按锁粒度` 的 3 个成员 → 位置 `[0,1,2]` → 连续 → 一个带块，`gridColumn: 1 / span 3`；
- `锁粒度对比`(matrix section) 的 3 个成员 → 位置 `[0,1,2]` → **同样一个带块，`gridColumn: 1 / span 3`**。

两段完全同区间，落在同一个 grid 轨道里重叠（截图里只能看到后画的 `锁粒度对比`）。行头写 `2 categories` 是对的，但**同一行无法同时显示"同一组原子的两种分类"**。

这是本次盘点最有价值的一条硬事实：**分类带的位置 = 语义，且当两个分类覆盖同一批原子时表达会互相吃掉。** 它不是视觉 bug，是"分类带用连续区间编码成员"这个编码方式本身的上限。

### 2.2 包含与嵌套：两种机制，别混

**（a）树包含 —— 存成边。**
`createTreeBindingEdge`（`treeBinding.ts:33-62`）把树父子关系写成
```
id: treebind:<parentTreeId>:<childTreeId>
source: 父知识节点  target: 子知识节点
type: belongs-to   label: contains   relationKind: structure
```
`belongsTo` 语义由 `containment.ts:3-4` 固定（`CONTAINMENT_EDGE_TYPE='belongs-to'`、`CONTAINMENT_EDGE_LABEL='contains'`），并带环检测（`wouldIntroduceContainmentCycle`）。

**（b）树的"投影用"包含边是单归属的。**
`buildTreeProjectionContainmentEdges`（`treeBinding.ts:160-200`）用 `assignedKnowledgeIds` 保证 **同一个知识节点只被赋予一个父**，首次命中即锁定（`:171-183`）。

**（c）组嵌套 —— 不存储。**
`GroupOverlay.tsx:38-40` 注释写得很直白：
> 跨度小的括号贴近内容，跨度大的依次外移——嵌套组（如 行记录 ⊂ 记录部分）不重叠

也就是说 `行记录 ⊂ 记录部分` 这个"嵌套"是**按成员矩形包络的跨度排序算出来的视觉结果**，数据里没有任何父子字段。`SemanticGroup` 只有 `{id, label, nodeId?, members[]}`（`types.ts:112-117`）。

**(d) 索引视图的嵌套框 —— 派生。**
`indexGraphLayout.ts:1047-1091`：由 `physicalContainmentEdges`（即 `belongs-to`）建 `childrenByGraphId` → `buildMosaicTree` → `layoutMosaicTree(..., depth+1)`（`:345-396`）递归 inset 出框，压进 `containmentFrames`。**框的层级 = 边的层级，框的大小 = 子内容重量。**

### 2.3 排列与布局：顺序是语义还是装饰

- **是语义，而且是最容易被静默改变的那种。** 分类带的 `start`/`span` 来自 `buildContiguousSegments`（`:190-230`），它读的是成员在 `orderedAtoms` 里的**下标**；`orderedAtoms` 来自维度顺序 + 每个维度 primarySection 的原子顺序（`:121-140`）。改任何一个原子的位置/增删一个原子 → 列的成员集合变 → 带块落的格子变。
- `stack` 布局里位置**完全**来自数据：`readPosition`/`readExtent` 读 `attrs` 上由 `config.positionAttr/extentAttr` 指定的键（`physicalProjection.ts:32-64`），`StackSection.tsx:27-45` 换算成 top/height。**这是唯一"位置本身是知识"的布局。**
- `matrix` 的单元格值是 `attrs[column.key]`（`MatrixSection.tsx`），列定义在 `config.columns`。
- 数据现实：`stack / tree / chain` **一个都没用**（见第 3 节），所以"位置承载含义"这套能力目前只在代码里成立。

### 2.4 连线

索引视图的边只有 3 类派生 + 2 类类型关系（`indexGraphLayout.ts`）：

| kind | 来源判定 | 常量位置 |
|---|---|---|
| `dependency` 依赖 | `type ∈ {uses, depends-on, needs-for}` | `:164` |
| `association` 关联 | `type ∈ {enables, leads-to, compares, relates-to}` | `:165` |
| `projection` 投影 | owner → `relationIndex.rootNodeId`（分裂根时才有） | `:1036-1043` |
| `extends` / `implements` | `KnowledgeEdge.relationKind` | `:661-681` |

箭头是四种 marker，各自配色（`UnifiedIndexGraph.tsx:1290-1306`），图例在 `:1221-1224`。边的 `dimensions` 字段**不做过滤，只做调暗**（`extractSubgraph.ts:175-177`）。

系统连接图是另一套：不区分 kind，把邻居所有边的 `type` 聚成一段文字（`systemConnectionGraph.ts:92-96`），只保留 in/out/both 方向（`:46-53`），最多 7 个邻居（`:44`）。

数据现实：`belongs-to` 一家占 3150/4070（其中 **2695 是树自动生成**，455 手工），真正的语义关系边是少数：`extends` 258、`instance-of` 252、`implements` 239、`transitions-to` 51、`depends-on` 12、`uses` 17……

### 2.5 正文与解释索引

- 索引方框的字段里直接写着 `/** 方框内直接显示的完整定义正文 */ content?: string`（`explanationIndex.ts:28`）。所以**索引视图的框不是"节点的小卡片"，是"带完整正文的可缩放方框"**。
- 树是 `Root → Tab → (子 tab + 页)` 无限递归（`:62-104`），`weight` 决定框在 mosaic 里的面积（`indexGraphLayout.ts:336`）。
- 反过来：工作区里点原子 → `setSelectedNodeOnly(nodeId)`（`DimensionCanvas.tsx:317-319`）→ 右侧解释卡。**图形结构指向正文靠的只有 `nodeId` 这一条线。**
- 分类带绑的逻辑节点也是同一套：`group.nodeId`，chip 点击 → `onGroupClick(nodeId)`（`GroupOverlay.tsx:67-69`）。
- 原子上的 `desc` 是**投影特化描述，只存本视图、不写回池节点**（`types.ts:64-67`；`DimensionCanvas.tsx:409-421` 明确注释"Existing pool node: only update the binding, never mutate the global node"）。
- 原子绑新节点时会**真的新建池节点**（`:411-416`）。
- 同一棵树还有第三种读法：**加时间层**（`TemporalRail` + `EventDrawer`），详见 §2.8。

### 2.6 问题卡

**问题卡（`types.ts:372-392`）**能引用的只有：`relatedNodeId` 一个、`answerSteps[]`（有序节点引用）、外加 `answer` 自由文本 + `kind/difficulty/source`。
现实（758 问）：

| 项 | 数 | 说明 |
|---|---|---|
| 总数 / 已答 | 758 / 738 | |
| 有答案文本 | 743 | |
| **有 answerSteps** | **0** | 字段从未被写入 |
| 指向知识节点 | 736 | |
| 指向树节点 / 池外 | 0 | |
| 无 relatedNodeId | 22 | |
| 带 `source`（文档来源） | 219 | |

结论很硬：**问题卡目前只能引用"一个对象 + 一段文本"，它引用不到维度、section、组、作用域或任何局部状态。** `q_lock_1` 的答案与 `demo_lock` 的 4 个 grid section 在语义上一一对应，但这个对应关系**没有任何机器可读的载体**。

**但写侧不是没有能力 —— 是没人用。** 系统里有一个完整的「答案 = 有序节点引用 + 自动合成草稿」的组装器（`QuestionAnswerEditor` + `answerComposer`），8 个字段全都能落盘。见 §2.11。这里把"能力缺失"和"能力闲置"分清楚：**`answerSteps` 不是没实现，是 758 个问题一次都没打开过它。**

（问题卡的 `kind` 枚举里有一个 `mechanism` 值，`QuestionKind.Mechanism`，`types.ts:338-345`。它只是**标签**，不触发任何机制投影——机制视图读的是 `KnowledgeNode.mechanismSpec`，两者无关联。）

→ **"结构含义"里，只有"谁属于谁"（边）和"谁被谁引用"（atoms/groups）落盘；"排成什么样"全是派生的。**

### 2.8 时态索引（`index` 视图的时间层）

**它不是一个独立视图。** TopBar 第 2 个 tab「时态索引 / Temporal Index」的 id 就是 `index`（`TopBar.tsx:10`），渲染的是 `TemporalIndexWorkspace`（`App.tsx:24, 160`）。它用的是**同一个** `UnifiedIndexGraph`、同一批方框/边/嵌套框（`indexGraphLayout.buildUnifiedIndexGraph` 同一个函数），只在外面套了三样东西：一条时间轴、一个事件抽屉、以及给节点加三种时态 class。

**而且默认看不见。** `TemporalRail` 在 `events.length === 0` 时直接返回 `null`（`TemporalRail.tsx:26`）。所以 `demo_lock` 那类节点根本没有时间层 —— 这也是为什么上一轮我把它漏了。

#### 数据形态（`data/evolution-events.json`，全库只有 2 条）

| 字段 | 含义 |
|---|---|
| `scopeRootId` | 这个事件属于哪个知识作用域（这里是 `k_java_fw_spring`「Spring」） |
| `occurredAt` | 时间点（渲染时按 UTC 格式化，`TemporalRail.tsx:4-11`） |
| `title` / `summary` | 阶段名与一句话说明 |
| `sourceOnlyNodeIds[]` | **来源证据**：读得到、但从索引里排除 |
| `introducedNodes[{nodeId, parentNodeId}]` | 本次**新增**的知识节点 —— **并且声明它挂在哪个父节点下** |
| `changes[{targetNodeId, facet, before, after}]` | 本次**变更**：改了哪个节点、哪个语义面、之前/之后 |

`facet` 是闭集，只有 4 个：`content 知识内容` / `structure 解释结构` / `metadata 知识元数据` / `projection 视图投影`（`timelineEvolution.ts:2-7, 31-36`）。**这里已经是一个"结构变化"的显式分类** —— `structure` 就是"解释结构变了"。

#### 时间切片怎么算（纯派生，`indexEvolution.ts:36-76`）

| 集合 | 算法 |
|---|---|
| `excludedNodeIds` | **所有**事件 `sourceOnlyNodeIds` 的并集（与当前切片无关，一律排除） |
| `visibleIntroducedNodes` | 前 `activeIndex+1` 个事件的引入节点**累积** |
| `hiddenIntroducedNodeIds` | 全部引入节点 − 可见 → 这些节点**变暗隐藏** |
| `currentIntroducedNodeIds` | 只有当前事件自己的引入节点 → 触发「新出现」 |
| `currentChangedNodeIds` | 只有当前事件自己的变更目标 → 触发「已改变」 |

#### 实测（Spring 作用域，树里 117 个节点）

| 项 | 值 |
|---|---|
| 作用域根 | `k_java_fw_spring`「Spring」（`role: group`） |
| 事件 | `Spring 4` @2013-12-12、`Spring 5` @2017-09-28 |
| `sourceOnlyNodeIds` 并集 | **3**：「Spring 4 新特性」「Spring 新特性之 Web 开发增强」「Spring 5 新特性」 |
| `allIntroducedNodes` | **5**（节点全部存在；**只有 1 个在树里**，另 4 个不在） |
| 「稳定知识」切片 | 可见新增 **0** / hidden **5** |
| 「Spring 4」切片 | 可见新增 2 / hidden 3 / 本次新增 2 / 本次变更 2（`content, structure`） |
| 「Spring 5」切片 | 可见新增 5 / hidden 0 / 本次新增 3 / 本次变更 3（`content, metadata, structure`） |

（「稳定知识」= `activeEventId: null` → `activeIndex = -1` → `visible = []` → 5 个引入节点全部隐藏，即回到事件之前的基线。与时间轴字幕「真正新增的知识会在对应时间点出现」一致。）

#### 结构由事件声明，且压过树投影 ← 这是最关键的一条

`temporalContainmentEdges`（`TemporalIndexWorkspace.tsx:329-352`）把包含边切成两半：

```
stableEdges    = 树的包含边
                 − source/target 落在 excludedNodeIds 的
                 − target 落在「所有曾被事件引入」的节点里的      ← 剔除
introducedEdges = 由事件的 parentNodeId 现场造：
                 id: timeline:<parentNodeId>:<nodeId>
                 type: belongs-to   label: contains            ← 与树绑定同一套语义
```

含义：**一旦某个节点被某个事件引入，它的树包含边就被剔除，位置改由事件说的 `parentNodeId` 决定。**

全库实测：
- 2695 条自动树包含边里，**只有 1 条**的 target 命中引入集合（`@Indexed`）—— 而且这条里事件声明的父（`k_vault_javaspringspring_7b4q3y`「Spring 注解」）与树里的父**本来就一致**（树路径：`Spring > Spring 注解 > @Indexed`）。
- **另外 4 个引入节点在树里没有任何位置**（`findTreePath` 返回空），它们在画布上的父节点 100% 来自事件声明。实测这 3 个被声明的父（SpringMVC 请求链路 / Spring 配置 / Spring 注解）都确实在 Spring 子树内，所以边能建起来（`:338-343` 有 `diagramScopeNodeIds.has(parentNodeId)` 门禁，父不在作用域内就静默丢弃）。

→ **结论：时态层是一条独立于树投影的"结构声明"通道。对那 4 个节点来说，它是唯一的结构来源。** 这也说明"结构"这个信息在系统里已经有两个来源（树绑定 / 事件声明），且事件优先。

#### 保存：准确说法不是"只读"

- **问题卡、机制视图、工作区（DimensionCanvas）完全读不到时间层**：`evolutionEvents` 唯一消费方就是 `TemporalIndexWorkspace`（全 `src/` grep 确认）。

### 2.9 机制视图（`mechanism` 独立视图）

**和时态索引相反：它是一个真正的顶级 tab。** `TopBar.tsx:11` 的 `VIEWS` 里 `id: 'mechanism'`、`label: '机制'`、`labelEn: 'Mechanism Lens'` —— 6 个 tab 里的第 3 个，`App.tsx:28` lazy 加载 `MechanismLensPanel`，`App.tsx:189-191` 在 `activeView === 'mechanism'` 时渲染。

它**没有自己的数据文件**。它是一台纯投影机：输入 = `nodePool` + `knowledgeEdges` + `treeData`，输出 = 一组派生图。没有任何「机制」的专属存储。

#### 它读什么：只有一个 `mechanismSpec`

知识节点上多出来的唯一字段（`types.ts:144`）：

```ts
mechanismSpec?: MechanismSpec;

interface MechanismSpec {            // types.ts:176-185
  phenomenonNodeId: string;          // 现象 = 哪个节点本身
  triggerNodeIds: string[];          // 触发事件
  participantNodeIds: string[];      // 参与者 / 资源
  stateNodeIds: string[];            // 状态（≥2）
  transitionEdgeIds: string[];       // 动态边（因果 / 状态转移）
  constraintEdgeIds: string[];       // 约束边
  outcomeNodeIds: string[];          // 结果
  failureNodeIds: string[];          // 失败路径
}
```

**它只引用 `id`，不引用任何视图结构。** 没有一条字段指向 dimension、section、原子、分类带或 group。

#### 归属怎么判：不是"选中机制节点"，是"就近归属"

`resolveOwningMechanismNodeId`（`knowledgeProjection.ts:210-238`）三级兜底：

| 级 | 条件 |
|---|---|
| 1 | 焦点节点自己 `kind === mechanism` → 就是它 |
| 2 | 沿焦点节点的**树路径向上**找最近的 `kind === mechanism` 祖先 |
| 3 | 若无：扫描全部 mechanism 节点，只要焦点节点有一条机制关系边连到某 mechanism 节点的**树作用域**内 → 归给它 |

→ 所以**普通节点也会显示机制视图**：选中 `k_1782820185793_jpet7h` 子树里的任意一个状态节点（比如某个 `state`），第 2 级就会把它归到「类的加载、链接与初始化机制」这个宿主上，画的是**宿主**的机制，不是这个状态自己的。这是"就近归属"而不是"精确匹配"。

#### 门禁：三关，缺一即空

`projectKnowledgeMechanism`（`:103-208`）返回 `null` 的条件：

| 关 | 判定 | 位置 |
|---|---|---|
| 1 | 无 `mechanismSpec` → `null` | `:127-128` |
| 2 | `validateMechanismSpec` 不过 → `null` | `:118` |
| 3 | **筛完后 `processEdges.length === 0` → `null`** | `:146-147` |

`validateMechanismSpec`（`validation.ts`）硬规则：

- `mechanism.kind !== Mechanism` → 错；
- `phenomenonNodeId !== mechanismNodeId` → 错（**现象必须是自己**，实测 8/8 都是自己）；
- 触发 / 参与者 / 状态 / 结果 **四类都不能空**；
- `stateNodeIds.length < 2` → 错（**状态机至少两个状态**）；
- `transitionEdgeIds` 不能空，且每条边 `relationKind` 必须是 `causality` / `state-transition`；
- `constraintEdgeIds` 每条必须是 `constraint`；
- 声明边的两端必须落在声明的节点集合内（实测 8/8 声明外端点 = 0）；
- 状态节点的 `kind` 必须是 `state`；触发节点的 `kind` **建议**是 `event`（**只给 warning，不拦**）。

第三关是最容易忽略的：**契约可以"验证通过"但仍投影不出东西** —— 因为筛选还要过"作用域"这一道（见下）。面板的两种空态正对应这两类：`机制定义不完整`（有错）vs `当前知识不构成机制`（无错但投影为空，`MechanismLensPanel.tsx:175-190`）。

#### 作用域：宿主子树 + 一跳非包含边

`collectMechanismCandidateNodeIds`（`:240-261`）：

```
候选 = collectTreeDescendantNodeIds(机制节点, 树序)      ← 子树全部后代
     + 任意机制关系边（非 structure）中，只要一端已候选 → 把另一端也拉进来
```

随后 `sourceEdges` 还要同时满足（`:138-145`）：边是机制关系、且若是 `belongs-to` 托管包含边则**两端都必须在声明集合内**、且两端都在候选集合内。

**实测：这条"边一跳"从来没生效过。** 我按代码复刻了候选集合，8 个机制全部 **拉入子树外节点 0 个**：

| 机制 | 子树节点数 | 边一跳拉入子树外 |
|---|---|---|
| `k_1782820185793_jpet7h` 类的加载、链接与初始化机制 | 28 | 0 |
| `k_1785934396536_as412a` 线程的状态 | 13 | 0 |
| `msr_flow` 复制流程（三线程） | 12 | 0 |
| `qproc_flow` 内部执行流程（六步） | 24 | 0 |
| `bcs_flow` Bean 创建策略机制 | 10 | 0 |
| `aop_flow` 执行阶段 | 11 | 0 |
| `tpl_flow` 线程池状态机（五状态） | 7 | 0 |
| `tio_flow` 传统 IO 执行流程 | 8 | 0 |

也就是说，**机制成员目前 100% 等于"宿主在树里的子树"** —— 那条"跨子树按边归属"的能力和 §3 里那批没用的词汇一样，是声明了但没被用到的。机制的子树的全部边也都已经落在子树内，没有任何跨树引用。

#### 4 类 knowledge 边 → 3 类机制边（其余全部拒收）

```ts
MECHANISM_RELATION_KINDS = { structure, causality, state-transition, constraint }   // :24-29
PROCESS_RELATION_KINDS   = { causality, state-transition }                          // :31-34

PROJECTED_RELATION_KINDS:                                                           // :36-47
  structure        → RelationKind.Contains
  causality        → RelationKind.RoutesTo
  state-transition → RelationKind.RoutesTo      ← 和因果合并成同一个
  constraint       → RelationKind.Locks
```

`classification / dependency / evidence / reference / comparison` **全部被拒**。代码注释原话（`:99-102`）：

> `Projects only explicitly typed dynamic knowledge into a mechanism. Ordinary concepts and ordinary graph relations are intentionally rejected.`

**为什么 `Caches / WritesTo / FlushesTo` 三个词汇永远是空的？根因在这条映射读的是 `relationKind`，不读 `type`。** 而数据里 `type` 恰恰是丰富的那一侧：

| 边 `type`（数据） | 条数 | 语义上对应哪个 `RelationKind` | 机制视图能表达吗 |
|---|---|---|---|
| `caches` | 1 | `Caches` | **不能**（映射表里没这条，且它连 `relationKind` 都没设） |
| `writes-to` | 3 | `WritesTo` | **不能** |
| `routes-to` | 10 | `RoutesTo` | 只能靠 `relationKind=causality/state-transition` 绕 |
| `guards` | 2 | 接近 `Guarded` 语气 | 不能（tone 也是自动算的） |
| `constrained-by` | 5 | `Constraint` | 只有同时把 `relationKind` 设成 `constraint` 才行 |
| `transitions-to` | 51 | `StateTransition` | 只有同时把 `relationKind` 设成 `state-transition` 才行 |
| `produces` / `triggers` / `calls` / `compares` / `contrasts-with` / `enables` / `needs-for` / `leads-to` / `depends-on` / `uses` / `belongs-to` / `extends` / `implements` / `instance-of` | 各若干 | 无对应 | 不能 |

→ **`type` 是自由文本（21 种取值），`relationKind` 是受控枚举（8 种），机制投影只认后者。** 所以那 3 个"永远空的词汇"不是没人写，是**写了也不走这条路**（`caches` 那条边的 `relationKind` 是空的）。这是 §3"代码词汇多于数据使用"的一个反向变体：**数据里有的语义，代码的词表接不住。**

#### 步序是派生的，不是存的 ← 和分类带同一类问题

`orderProcessRelations`（`:320-365`）：**BFS 遍历**。

```
origin = 机制节点自己（若它有出边）
       → 否则：第一个「入度 0 且有出边」的候选节点
       → 否则：第一条边的 source
队列 BFS：从 origin 出发，每到一个节点就按「目标在树序里的下标 → 源下标 → 边 id」排序后出边
剩余未被访问的边：按同一比较器排序后追加到末尾
```

→ **机制图的"第几步"完全由 `collectTreeDescendantNodeIds` 的树遍历顺序 + BFS 决定。** 数据里没有任何字段写"这是第 3 步"。改树里节点的位置、或加一条边，步序会静默改变。这与 §2.3 分类带"位置即语义"是同一个性质。

#### 视觉语气也是派生的，6 种只生产 3 种

`VisualTone` 声明了 6 种（`core.ts:17-24`）：`Active / Traversed / Mutated / Guarded / Persisted / Released`。
实际生产点（全 `src/` grep，排除枚举定义与 CSS 映射）：

| tone | 生产点 | 何时 |
|---|---|---|
| `Traversed` | `knowledgeProjection.ts:188` | 每一步的 **source** |
| `Active` | `knowledgeProjection.ts:180`；`diagram.ts:92`；`lens.ts:130/174` | target **还有出边**（流程未完）／兜底默认值 |
| `Persisted` | `knowledgeProjection.ts:181` | target **无出边**（流程终点） |
| `Mutated` / `Guarded` / `Released` | **无** | 有 CSS class（`is-mutated/is-guarded/is-released`）但**从未被赋给任何东西** |

→ "当前步的起点 = 已走过、终点 = 活的还是终态"这套语气是**自动算出来的**，作者写不了"这一步是加锁"。

#### 布局也是派生的（三维，且第三维编码边类型）

`buildScenePositions`（`lens.ts:181-219`）：

```
depth = deriveTraversalDepths(model, origin, DEFAULT_TRAVERSAL_KINDS)   // 6 种 kind 全算
x = depth × 180
y = 同深度内按 entities 数组顺序居中排 × 96
z = relationKindHeight × 48
```

`relationKindHeight`（`:221-238`）取该实体**第一条**相关边的 kind 在 `[Contains, RoutesTo, Caches, WritesTo, Locks, FlushesTo]` 里的下标 —— 也就是**用"层高"编码关系类型**。但该数组里 `Caches / WritesTo / FlushesTo` 三个从无生产点（投影只出 Contains/RoutesTo/Locks），所以 z 实际只有 3 档可用。

`x` 来自 BFS 深度、`y` 来自**树序遍历**（`sourceNodeIds` 的顺序就是 `collectTreeDescendantNodeIds` 的顺序）。**三轴的语义全部来自树序 + 边类型，没有一个来自存储。**

#### 图型：声明 4 种，可选 3 种，可达 3 种

`MechanismDiagramType`（`diagram.ts:10-15`）= `Structure / Flow / Logic / Sequence`。
但 `DIAGRAM_OPTIONS`（`MechanismLensPanel.tsx:42-61`）只列 `Logic / Flow / Sequence` —— **`Structure` 从未出现在 UI 里，全 `src/` 无任何引用点**（grep 确认）。

它现在已经具备：

| 能力 | 实现 |
|---|---|
| 显式声明关系而不是靠推断 | 8 个 id 数组（`types.ts:176-185`） |

### 4.6 三层的 `tag` 标注 + `domainPathsByNode` —— 现成的"同一陈述在多处出现"观测面

这是读 Tag库才补上的一块：**`tags` 不是节点级字段，它同时存在于节点 / tab / 子页三层**（`KnowledgeNode.tags`、`ExplanationTab.tags`、`ExplanationPage.tags`，后者被前者继承）。

它带来的东西恰好是"本体 vs 实例"讨论里最缺的那个观测面：

| 能力 | 实现 | 数据厚度 |
|---|---|---|
| **同一 tag 跨节点聚合** | `collectSupertagMaterialGroups` 扫全池，把三层 tag 扁平成"材料" | **5522 个 tag / 29638 个材料**（实拍） |
| **标注可以落在结构内部，不只在对象上** | tab 级 / page 级 tag，selection 直接指到 `{nodeId, tabId, pageId}` | 一个 tag 可横跨 375 个节点（`method` 组实拍） |
| **"这段话说的是同一件事"的判据** | `supertagMaterialSignature` = 归一化后整段内容相等 → `N 段一致` / `独有表述` | 实拍生效，但粒度=全文（见下） |
| **一个知识点挂在多个树路径下** | `domainPathsByNode` 用 `collectTreeReferencesByNodeRef` 列出**全部**路径并显示 | **全系统唯一把 §5 第一处那 88 个重复 nodeRef 摆上界面的地方** |

**这就是"本体在池、差异在路径"旁边已经站着的第二个观测面**：§4.1 的 `supplement` 管"差异正文放哪"，这里的 tag 管"同一标注散在哪几处"。前者是**给定路径看差异**，后者是**给定标注看全部分布**。

**但它现在测不准**：签名是"整段文本归一化后完全相等"，实拍里三列内容几乎逐字相同（都含同一段"继承父类型对应成员的文档说明"和同一串异常列表）仍全判 `独有表述`，因为方法声明行 `public boolean add(E)` 与 `public boolean addAll(java.util...` 不同。**它只能发现"逐字复制"，发现不了"语义相同、措辞微差"** —— 而这正是"同一概念在 N 个领域各说一遍"最常见的形态。

→ 结论：**"同一表述散了多远"这件事，系统已经有观测入口（tag × 三层 × 内容签名），只是判据粒度停在全文级。** 要提升粒度，改的是 `supertagMaterialSignature` 一个函数，不需要新机制。

## 5. 四处已经存在的硬问题（必须先知道）

前三处是"不一致"，第四处是"一碰就崩"，但都属于"动手前必须先知道"。

**第一处不一致：树是多归属，边是单归属。**

`buildTreeProjectionContainmentEdges` 是单归属（首次命中锁定），但**树本身是多归属的**：

| 项 | 数 |
|---|---|
| 重复 `nodeRef`（同一知识节点挂在多个树节点下） | **88 个** |
| 涉及树节点 | 182 |
| 其中跨一级分支（如 计算机科学 vs 数学） | 8 |

实例：`统计学` / `信息论` / `数值分析` 同时挂在 `计算机科学 > 计算数学` **和** `数学` 底下；`RAID` 同时在 `硬件` 和 `系统组织 > 操作系统` 下。

含义：**树是"多归属导航"，边是"单归属结构"，两者已经不一致。** 任何基于"一个知识只属于一处"的推理，在树这一侧会遇到 88 个反例。这不是我要修的东西，但它是判断"融合节点"时会直接踩到的地方。

**第二处不一致：结构有两个来源，且互相覆盖。** 树投影写 `treebind:` 边，时态事件写 `timeline:` 边，语义相同、优先级不同（事件赢）。现在只有 1 条边真正产生覆盖（`@Indexed`，且两边的父恰好一致，所以看不出差别），但那 5 个引入节点里有 **4 个在树里根本没有位置** —— 它们的存在感完全由事件维持。这意味着：**如果只看树，这 4 个节点是"孤儿"；只有走时态层才看得到它们挂在哪儿。** 做任何"谁属于谁"的批量判断前，必须先把 `introducedNodes` 纳进来，否则会漏掉这 4 个。

**第三处不一致：词汇表与数据不闭合。** 三处都实测过：

| 现象 | 数据 | 枚举/代码 |
|---|---|---|
| **同一个语义有两种大小写** | `kind: 'concept'` 106 个 + `kind: 'Concept'` 203 个 | 枚举只有 `concept`（`types.ts:51`）→ **203 个节点的 kind 对不上枚举** |
| **边关系越界** | 4 条边 `relationKind: 'comparison'`（`contrasts-with`） | `KnowledgeRelationKind` 里**没有** `comparison`（`types.ts:187-196`）；`comparison` 是另一套枚举 `ExplanationIndexRelationKind` 的值 |
| **枚举值零使用** | `classification` 0 条、`evidence` 0 条 | 枚举里都声明了 |
| **"自称机制"≠"可投影为机制"** | `kind='mechanism'` 20 个，能开视图的 **8 个** | 投影只认 `mechanismSpec`，不认 `kind` |

含义：**任何按 `kind` 或 `relationKind` 做等值匹配的统计/迁移，都会静默漏掉这些行。** 203 个 `Concept` 节点在"按 kind 分组"的代码里会掉进"未知分支"；4 条 `comparison` 边在机制投影里被拒收（本来也拒收，但它在任何按枚举穷举的地方都是漏洞）。

**第四处：节点库搜索会白屏整个应用（实测复现）。**

在「节点库」搜索框输入任意关键词 → `document.body` 变空、React 整棵树卸载。视口里只剩深色背景。

捕获到的一手错误（用 `window.onerror` 钩子取到）：

```
Uncaught TypeError: Cannot read properties of undefined (reading 'toLowerCase')
  @ http://127.0.0.1:4173/assets/NodeDatabase-yRGUNNgk.js:1
```

根因是 `NodeDatabase.tsx:47-51` 的搜索过滤 —— **同为必填字段，两处做了保护、两处没做**：

```ts
node.label.toLowerCase().includes(query)                            // ✗ 无保护
  || node.card?.title?.toLowerCase().includes(query)                // ✓ 有
  || node.card?.tabs?.some(tab => tab.content.toLowerCase()...)     // ✗ 只保护了 tabs，没保护 content
```

`label` 与 `content` 在 `types.ts` 里都是**必填 `string`**，所以一旦池里混进不符合 `KnowledgeNode` 形状的条目，搜索一次就直接炸。运行态核对结果：

- 池里共有 3843 个正常节点，**外加一个 id 为 `error`、值为字符串 `"Missing file parameter."` 的顶层条目**
- 它 `label === undefined`、`card === undefined` → 命中 `node.label.toLowerCase()` 那一支
- **`data/node-pool.json` 文件里 grep 不到 `Missing file parameter.`**（全文无匹配）→ 说明它不是磁盘上的数据，是运行期被 `/api/data` 数据中间件（`vite.config.js`）注入/合并进来的

**这件事的两个含义**

1. **一个不合格的条目能让整个应用不可用，而且没有任何错误边界接住。** 崩溃点在 `useMemo` 里（`filteredNodes`），React 会卸载整棵树；`window.onerror` 能抓到，但界面只给白屏。这是本轮实测发现的最严重的一条。
2. **它是"字段是必填 string"这个假设的反例。** §5 第三处已经证明数据里有越界枚举值（`Concept`、`comparison`），这里更进一步：**连必填字段都可能缺席**。任何"照类型定义直接取字段"的代码都在同一类风险下 —— 节点库卡片视图的 `node.card.tabs[0].content.substring(0, 100)`（`:359`）也是同一形态，只是暂时没被触发。

## 6. 对"通用归本体、具体差异留自身"的直接影响（事实约束，不是方案）

按你的要求，不给方案，只给从上面事实里**直接推出来的约束**：

1. **差异的特化原本就写在容器里，不在节点上。** 三个落点已经存在：`AtomBinding.desc/attrs`（视图内特化，`DimensionCanvas.tsx:409-421` 明确保证不改池节点）、`treeNode.supplement`（路径特化，14 处在用）、`SemanticGroup.nodeId`（把一组差异升格成一个逻辑节点）。**不需要新机制来表达"差异"。**

2. **"结构"目前没有可引用的载体，只有派生结果。** 分类、顺序、分组只活在 `viewDimensions` 里（27 个节点有），而且排成什么样是每次重算的。问题卡（`answerSteps` 使用率 0）、机制视图（`mechanismSpec` 8 个）、索引视图都读不到它。所以"把结构也迁到本体"这件事，**现有能力里没有对接点**。

3. **改原子的 `nodeId` 引用 ≠ 改正文引用，会同时改结构含义。** 分类带的 `start`/`span` 依赖 `orderedAtoms` 的下标序列。融合两个节点、把两个原子并成一个、或改变某个原子的位置，都会让至少一个带块的格子位置变化。**正文一字不丢、结构静默变形，是这条路径上最容易发生的事。** 你上一轮担心的正是这个，而它是可以用 `buildContiguousSegments` 的输出做前后对比来验证的。

4. **`canonicalKey` 是现成的、无副作用的挂点。** 641 个节点已有它、零消费方。任何"同义合并"的账都可以先记在这里而不动别的字段。

5. **`shared` / `locked` 不是语义字段，别当锚点。** `shared` 只在节点库当个 `⟳` 徽章，`locked=0` 个节点在用。

6. **"未声明 scope"的 30 个维度全走默认 `parts`。** 也就是说现在绝大多数维度根本没回答"我这一行分类的是谁"这个问题——`object`/`parts` 的区分只在「页 / page」一个节点上真正用过。这个字段的表达力远未被验证。

7. **"结构"有两个来源，不是三个。** 树包含边（`treebind:` / `treeprojection:`）和事件声明（`timeline:`）都是"谁挂在谁下面"；而**分类/排序/分组只活在 `viewDimensions` 里，且不落盘**。所以"把结构迁到本体"这件事，现有能力里**只有树和事件这两个挂点**，而它们表达的都是 containment 一种关系。

8. **时态层提供了一条已经跑通的"声明式结构"通道，但它现在只服务 5 个节点。** 如果要验证"结构变更"这条路，`introducedNodes[].parentNodeId` + `changes[].facet === 'structure'` 是现成的、语义完备的载体 —— 比新造机制更省事，且它已经有只读门禁（选了事件就禁止编辑）保护历史。

9. **"显式声明动态"这条路已经被走过一次（`mechanismSpec`），走通的只有"声明 + 校验 + 投影"，没走通的是"表达复杂动态"。** 8 个样本已经暴露出上限：**单触发**（`triggerNodeIds` 8/8 恒为 1 个）、**无分支**（`Process` 是一条线性 `steps`，没有分支/循环/并发/条件的槽）、`failureNodeIds` 名义上是"失败路径"但**投影代码从不读它**（只在 `declaredMechanismNodeIds` 里参与端点校验）、`constraintEdgeIds` 2/8 非空、显式 `causality` 只在 1 个节点出现 2 条。任何"用声明表达动态"的新方案，要么复用这个形状，要么必须解释为什么不复用。

10. **机制图的"步序 / 坐标 / 高亮"全部派生 —— 这是"顺序即语义"的第二个实例。** `x` = BFS 深度、`y` = 树序遍历、`z` = 边类型下标、第几步 = 树序 + BFS（`lens.ts:181-219`、`knowledgeProjection.ts:320-365`）。它们**没有任何一个落盘**。所以改机制子树的树序或边集合，会静默改变"这是第几步、摆在哪、哪一步亮"。加上分类带的 `start`/`span` 和声明的端点集合，**目前一共有三处"只改引用、静默改结构含义"的地方**，做"融合节点"前都要用前后对比跑一遍。

11. **"答案由节点组装"已经实现了，但答案正文是一次性快照。** `composeQuestionAnswerDraft` 取每个步骤节点的**第一个 content 非空的 tab**拼成文本（`answerComposer.ts:4-6, 25-46`）；保存后 `answer`（文本）与 `answerSteps`（骨架）各自独立，**没有反向同步**。所以"本体的正文改了、下游文本跟不跟"这件事在这里已经有了第一个样本：**不跟**。任何方案必须回答：答案/问题这类"引用节点的一段文本"，算不算差异？如果算，它现在**没有挂载点**——它是快照，不是引用。

12. **"同一表述散了多远"已经有现成观测面，但判据停在全文级。** tag 三层（节点/tab/子页）× `supertagMaterialSignature` × `domainPathsByNode` 已经构成"标注分布 + 内容一致性 + 多路径归属"的组合（§4.6），5522 tag / 29638 材料是现成的样本量。要做"通用归本体"的效果验证，这套比新造指标省事得多；但签名粒度必须先细化到段落级，否则"语义相同、措辞微差"一个都抓不到。

13. **多归属不只出现在树上，问题卡的归属踩的是同一条缝。** `moveQuestionToNode(questionId, treeNodeId)` 要落到该树节点的 `nodeRef` 才成立，而同一个 `nodeRef` 可能挂在 88 个重复位置中的任意一个（§5 第一处）。**"把问题移到哪个目录"在树这一侧本来就是多解的。** 任何"一个知识只属于一处"的迁移，都会顺带改写问题卡的归属。

14. **必填字段也会缺席，而代码按类型定义直接取。** `label` 与 `tab.content` 在 `types.ts` 里都是必填 `string`，但池里存在 `label === undefined` 的条目，一读就白屏（§5 第四处）。**"照类型定义取字段"在这份数据上不成立。** 任何遍历全池的操作，第一件事应该是形状校验（`typeof x === 'string'`），而不是直接读 — 这不是防御性编程建议，是这份数据已经证明的必需条件。
