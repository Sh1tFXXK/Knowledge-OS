## 11. 判定与处置方案

> ⚠️ 本节是**判定**，不是脚本读数；但所有基数均引用上文由脚本算出的值。

### 11.1 结论：**不建议把 `类` 并入 `类库`**
- **无可合并的冗余**：共享实体 **0** · FQCN 名字交集 **0** · 正文逐字节重复 **0**。
  ⇒ 与 C 批（平行库树、真超集）/ D 批（近似超集、27 重叠方法）的动机**根本不同**：那两批都是「同一内容出现两次」，本对**一次都没有**。
- **不是同一根轴**：`类库` = 以「具体类 / 功能组」为条目的**类目录**（22 直子 · 164 tabs · 138701 字）；`类` = 名义「类」概念、实际是 **java.lang 包**（1 直子 · 2 tabs · 8011 字，最大深度 4）。
- **粒度不同**：`类库` 里一个类 = 一个实体（tabs 装方法）；`类` 里一个类被拆成「类节点 + 分节子节点」。直接合并会把两套建模约定混在一棵树里。

### 11.2 扫描出的真问题：`类` 是「身份与内容错配 + 概念家族被拆散」
- **身份**：`类` 持有 `canonicalKey = java:class`（全库 canonicalKey 严格 1:1，**0** 组重复 ⇒ 这是可信的硬身份键）。
- **出身**：同族概念 `变量`（`java:class:variable`）、`修饰符`（`java:class-modifier`）都团聚在 `Java syntax > 数据类型 > 引用类型 > Java类` 下；**只有 `类` 孤悬在 java 顶层**（挂载数 1）。
- **内容**：`类` 树下 10 个节点里，**没有任何一个是「类」这个概念本身** —— 全是 java.lang 包的具体类与文档片段。
- **机械分类查出的错配候选**（见 §10）：
  - `java.lang` → **包占位节点**（末段小写 ⇒ 是包不是类）
  - `java.lang / Object / Math / 常见方法` → **表格型分节**（正文以「序号」表头开头）
  - `java.lang / Object / 类的构造函数` → **短片段**（20 字）
  - `java.lang / Object / 方法` → **表格型分节**（正文以「序号」表头开头）
  - `java.lang / Object / Optional / 方法` → **表格型分节**（正文以「序号」表头开头）

**人工核对补充（脚本判不了，已逐条读原文）**：
- `Object / 类的构造函数` 正文 = `**Object()** 构造一个新对象` ⇒ 是 **Object 自己的分节**，不该与 Number/Math/Optional 做兄弟。
- `Object / 方法`（2703 字）正文表头为 `序号 | 方法 & 描述`，首几行是 `clone()` / `equals(Object)` / `finalize()` / `getClass()` ⇒ **是 Object 的方法表**，同样是 Object 的分节。
- `Object / Math / 常见方法`（864 字）正文是 `xxxValue()` / `compareTo()` / `valueOf()` ⇒ **是 Number 的方法表**，且**父节点是 Math** ⇒ **归错父**（Math 与 Number 是两个类）。
- `Object / Optional`：Optional 属 `java.util`，不是 `java.lang` ⇒ **包归属错**（挂在 `java.lang` 下）。
- `java.lang`（rc=36 字）=「Java 包 `java.lang`，包含本次导入范围内直接声明的类型。」⇒ **导入器生成的包占位节点**（无 canonicalKey）。

### 11.3 三档处置方案（Δ 需另开 plan 阶段精算）
- **方案 A · 只正名，不动结构（最小动作）**：不合并；把 `类` 改名为能自述的词（如 `java.lang 包`）并补 rootContent，消除与 `类库` 的命名歧义。
  - 触及：1 个树 name + 1 个池实体（label/rootContent）。**不删任何节点、不动任何边。**
  - 代价：保留了「概念键 `java:class` 挂在 java.lang 内容上」这个错配，只是把它藏起来。
- **方案 B · 拆身份与内容（推荐）**：
  - ① `类`（`java:class`）**归位**到 `Java syntax > 数据类型 > 引用类型 > Java类` 下，与 `变量`/`修饰符`/`内部类` 团聚（纯换挂载，实体不删）。
  - ② 其内容按类归位：Object 的两个分节（`类的构造函数`/`方法`）原子化进 `java.lang.Object` 的 tabs；`Number`/`Math`/`Optional` 各自挂到 `类库`（注意 `Optional` 应标 `java.util.Optional`）；`Math/常见方法` 纠正为 Number 的方法表。
  - ③ 导入占位节点 `java.lang` 卸树（其 rc 仅一句导入说明）。
  - 触及：树结构（多节点重挂 + 卸树）、池（Object 加 tab、若干实体改 label）、边（父边换端点）。**这是本批唯一有实质收益的方向**，但也最接近一次结构批次。
- **方案 C · 整体并入（不推荐）**：把 `类` 11 节点直接挂到 `类库`。会在 `类库` 里同时出现「扁平 FQCN 类条目」与「类节点 + 分节子节点」两套形态；且 `类的构造函数`/`方法`/`作用` 这些**分节片段在 `类库` 的粒度下无处安放**（`类库` 下除 Files>最佳实践、Enum>用法 外无子节点）。

**建议**：若只想要「不再混淆」，走 A；若要让 java 子树真正收敛，走 B（需另开 plan 阶段，像 D 批那样先出逐项 diff 再裁决）。**C 不建议**。
